# Deploying the October 2026 release (branch `fix/job-card-leaks`)

What this release contains: the Steps 1–7 job card workflow, roles and
responsibilities, the CRM cycle, the intake inspection (on screen or paper
upload, customer signature and customer link), the Team Board, the technician
app (`/mechanic`, scan by job-sheet QR / VIN / typed number), the Vehicle Status
Board (`/vehicle-board`, replaces Service Tracking), the workshop customer
portal (`/customer/*`), workshop wording ("Ready for collection") and the
security fixes. Full notes: `HANDOVER.md` §3 (database), §5a–5c.

Do the steps in order. Every migration is idempotent, so re-running one is safe.

---

## 0. Before you start

- **Back up the database and the uploads first.**

  ```bash
  mysqldump -u <DB_USER> -p --single-transaction --routines <DB_NAME> > backup_$(date +%F).sql
  tar czf uploads_$(date +%F).tgz car-workshop-backend/uploads car-workshop-backend/private-uploads 2>/dev/null
  ```

- **Never run the QA suites (`car-workshop-backend/scripts/qa/*.mjs`) against
  production.** They create users and data, then delete every row above their
  start id in every table. They refuse to run unless `DB_HOST` is local, but
  don't rely on that.
- **Do not create the `qa_*` test accounts** in production; they exist only on
  the development Mac.

## 1. Get the code

```bash
git clone https://github.com/osamahkenawy/pioneer-workshop.git
cd pioneer-workshop
git checkout fix/job-card-leaks
```

(or `git fetch && git checkout fix/job-card-leaks && git pull` in an existing clone)

## 2. Install dependencies

```bash
cd car-workshop-backend && npm ci && cd ..
cd car-workshop-frontend && npm ci && cd ..     # new: @zxing/browser (VIN / QR scanning)
```

## 3. Environment (`car-workshop-backend/.env`)

Copy the `.env` from the current server (it is not in git). Then check these
— they are new or now matter (all documented in `.env.example`):

| Variable | Production value | Why |
|---|---|---|
| `FRONTEND_URL` | `https://<your app host>` (no trailing slash) | Every customer link is built on it: status page, inspection link, estimate approval, portal set-password. A wrong value sends customers to a dead link. |
| `NODE_ENV` | `production` | |
| `DISABLE_CRON_JOBS` | `false` on the one main server | Runs reminders, parts-arrival alerts, job-delay checks. |
| `ENABLE_DATA_RETENTION` | `false` | Inherited job that **deletes** old data. |
| `ENABLE_ACCEPTANCE_TIMEOUT` | `false` | Inherited job that **un-assigns** technicians. |
| `ENABLE_TRIAL_ENFORCER` | `false` | Inherited job that suspends workshops. |
| `ALLOW_PUBLIC_SIGNUP` | `false` | Customers get portal access from staff ("Give portal access"). |
| `ENABLE_API_DOCS` | `false` | |
| `SMTP_*` | the mail account | Without it, e-mail sends report "The e-mail was not sent" (WhatsApp / copy link still work). |

Frontend: the build uses `VITE_API_URL` (default `/api`, which is right when
nginx serves the app and proxies `/api` to the backend on the same host).

Create the private upload folder (inspection paper forms; never served publicly):

```bash
mkdir -p car-workshop-backend/private-uploads/inspections
```

## 4. One check before the migrations

`20261011_invoice_number_unique.sql` adds a unique index; it cannot build while
duplicate invoice numbers exist. Run this — it must return **no rows**:

```sql
SELECT workshop_id, invoice_number, COUNT(*) AS n
  FROM invoices
 GROUP BY workshop_id, invoice_number
HAVING COUNT(*) > 1;
```

If it returns rows, renumber the duplicates (keep the oldest, give the others a
new `INV-…` number) before step 5.

## 5. Run the migrations (in this order)

From `car-workshop-backend/`:

```bash
DB=car_workshop        # your database name (DB_NAME in .env)
for f in \
  20261006_job_card_billing.sql \
  20261008_job_card_approvals.sql \
  20261011_invoice_number_unique.sql \
  20261012_workshop_workflow.sql \
  20261013_roles_workflow.sql \
  20261014_crm_cycle.sql \
  20261015_intake_integrity.sql \
  20261016_inspection_documents.sql \
  20261017_inspection_share_sign.sql \
  20261018_customer_portal_invite.sql \
  20261018_pregenerated_barcode_width.sql \
  20261018_technician_pause_reason.sql \
  20261019_inspection_signed_via_portal.sql \
  20261019_workshop_manager_settings.sql
do
  echo ">> $f"
  mysql -u <DB_USER> -p"$DB_PASS" "$DB" < "src/migrations/$f" || { echo "FAILED on $f"; break; }
done
```

| # | File | What it does |
|---|---|---|
| 1 | `20261006_job_card_billing.sql` | Itemised billing on job cards (`work_orders.billing_basis`, item types, decimal quantities) |
| 2 | `20261008_job_card_approvals.sql` | Customer approval on job cards; Supervisor/Manager sign-off on external estimates |
| 3 | `20261011_invoice_number_unique.sql` | Unique invoice number per workshop (needs step 4 first) |
| 4 | `20261012_workshop_workflow.sql` | Steps 1–7: sub-job cards, Pause, Store availability + expected date, Genuine/After-Market pricing, collection contacts, Storekeeper role |
| 5 | `20261013_roles_workflow.sql` | Role responsibilities (`roles.capabilities`) and menu keys |
| 6 | `20261014_crm_cycle.sql` | CRM cycle links (enquiry ↔ estimate ↔ booking), Bookings menu |
| 7 | `20261015_intake_integrity.sql` | Step 1 classification kept on each job |
| 8 | `20261016_inspection_documents.sql` | Inspection on screen or paper upload |
| 9 | `20261017_inspection_share_sign.sql` | Customer signature + customer link on inspections |
| 10 | `20261018_customer_portal_invite.sql` | "Give portal access" |
| 11 | `20261018_pregenerated_barcode_width.sql` | Longer, unguessable status tokens |
| 12 | `20261018_technician_pause_reason.sql` | Pause reason/note, technician scan lookups |
| 13 | `20261019_inspection_signed_via_portal.sql` | Signed "in the customer portal" |
| 14 | `20261019_workshop_manager_settings.sql` | Workshop Manager sees Settings (Users / Roles) |

**If the target database is older than mid-September 2026** (restored from an
old dump), first run the earlier ones the same way, in filename order:
`20260903_*` … `20260917_work_order_intake_redesign.sql` (all idempotent).
Never run `src/migrations/car_workshop.sql` on an existing database — it is the
full base dump for a brand-new install only.

## 6. Check the migrations landed

```sql
-- each line must return 1
SELECT COUNT(*) = 1 FROM information_schema.columns WHERE table_schema = DATABASE() AND table_name = 'work_orders'          AND column_name = 'customer_approved_at';
SELECT COUNT(*) = 1 FROM information_schema.columns WHERE table_schema = DATABASE() AND table_name = 'job_cards'            AND column_name = 'parent_job_card_id';
SELECT COUNT(*) = 1 FROM information_schema.columns WHERE table_schema = DATABASE() AND table_name = 'roles'                AND column_name = 'capabilities';
SELECT COUNT(*) = 1 FROM information_schema.columns WHERE table_schema = DATABASE() AND table_name = 'vehicle_inspections'  AND column_name = 'share_token';
SELECT COUNT(*) = 1 FROM information_schema.columns WHERE table_schema = DATABASE() AND table_name = 'customers'            AND column_name = 'portal_invited_at';
SELECT COUNT(*) = 1 FROM information_schema.columns WHERE table_schema = DATABASE() AND table_name = 'technician_time_logs' AND column_name = 'pause_reason';
SELECT COLUMN_TYPE LIKE '%portal%' FROM information_schema.columns WHERE table_schema = DATABASE() AND table_name = 'vehicle_inspections' AND column_name = 'signed_via';

-- roles: Storekeeper exists, Workshop Manager has Settings
SELECT slug, JSON_CONTAINS(modules, '"settings"') AS has_settings FROM roles WHERE slug IN ('storekeeper', 'workshop_manager', 'team_leader');
```

## 7. Build and restart

```bash
cd car-workshop-frontend && npm run build && cd ..   # serve dist/ (nginx root)
cd car-workshop-backend && pm2 restart car-workshop-backend && cd ..   # the pm2 name used by deploy/deploy.sh
```

nginx must send every app path to `index.html` (SPA fallback), including the new
ones: `/mechanic…`, `/vehicle-board`, `/customer/…`, `/inspection/<token>`,
`/service-status/<token>`, `/track/<token>`.

## 8. After the restart (in the app, as the owner / Workshop Manager)

1. **Customer message templates** (optional, recommended): Notifications →
   Templates → **Reset to defaults**. The workshop still has the old courier
   texts ("ready for pickup!", "Vehicle Returned", "Cash Payment Collected").
   The reset replaces them with the four workshop messages (job opened, ready
   for collection, closed, cancelled). This changes the workshop's saved
   templates — skip it if they were customised on purpose.
2. **Settings → Roles**: check each role's responsibilities and menu.
3. **Settings → Users**: give the Team Leaders their technicians (Team Board →
   Manage team), and create technician logins for those who will use the app.
4. **Customers → a customer → Give portal access** sends that customer a
   set-password link for `/customer/login`.

## 9. Smoke test (10 minutes)

- Staff login → Dashboard → "Your tasks" loads.
- Work Orders → New Work Order → open a job card (odometer is optional).
- Job card → Step 4 → Technical inspection → mark damage → Customer not
  present → Complete → Send to the customer → open the link in a private window.
- Vehicle Status Board, Team Board and `/mechanic` (as a technician) open.
- `/customer/login` shows the customer portal sign-in.
- The backend log shows no errors.

## 10. Security follow-up (still open)

Older commits contained real passwords in `deploy/*.txt` / `deploy/*.sh`
(now replaced with placeholders, but still in git history). **Rotate the
database password and `JWT_SECRET` on the server** if that has not been done.
Rotating `JWT_SECRET` signs everyone out once.
